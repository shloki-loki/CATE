# T0018: Asset pipeline design for Neon Coast

Agent: claude-1. Date: 2026-11-26. Status: design. No game code lands in this task. T0019 creates `game/`, and the generators below are built in the tasks that need them (see §10).

This document expands §3.9 of the approved architecture (`data/outputs/T0016.md`) and stays inside the Three.js/WebGL2 decision confirmed in `data/outputs/T0017.md`. Fixed inputs I did not change: glTF 2.0 binary, meshopt compression, 1 unit = 1 m, +Y up, models face +Z, wheel nodes `wheel_FL/FR/RL/RR`, ids `category.name##`, everything original (the §0 content rule).

**I tested the core of the pipeline before writing this** (§9): a code-built low-poly car went through Three.js `GLTFExporter` in Node 24, then glTF-Transform meshopt compression, then the Khronos glTF validator. The result had 0 errors and 0 warnings, the output was byte-identical across two runs, and the file went from 22,632 to 5,236 bytes. So the toolchain below has been run, not just guessed.

## 3. Shared rules for every generator

1. **Units and axes:** 1 unit = 1 m, +Y up, front faces **+Z** (glTF convention), right-handed.
2. **Origins:** buildings sit at the footprint centroid on the ground (y = 0). Vehicles sit at the midpoint between the axles at ground height with the wheels touching y = 0 at rest. The character's origin is between the feet on the ground. Props sit at the bottom centre. Weapons use the grip point.
3. **Determinism:** every generator takes `(params, seed)` and uses one seeded PRNG (`mulberry32`) in `game/src/shared/rng.ts`, shared by tools and runtime. Seeds per item are `hash32(citySeed, chunkX, chunkZ, index)` at runtime and `hash32(assetId)` at build time. `Math.random()` is banned by lint in generators. Same inputs must give byte-identical output (tested, §9).
4. **Materials are a contract, not data:** materials are named from a fixed list (§8.3). At load time `AssetLoader` swaps each named material for the shared instance in `render/materials.ts` (`MaterialLibrary`). Fewer distinct materials means fewer shader programs and better batching (T0016 §5, ≤ 600 draw calls). The colours exported in the `.glb` are fallbacks.
5. **No textures inside `.glb` files in v1:** vehicles, the character, weapons and props use flat PBR values and vertex colours. That keeps files at a few KB and avoids any image codec in Node.
6. **Triangle budgets** (checked by the build, §7.3) are derived from T0016 §5 (≤ 1.5 M visible triangles, about 40 cars, about 60 peds, 5 × 5 chunks):

| Asset | LOD0 | LOD1 | LOD2 |
|---|---|---|---|
| Vehicle | ≤ 3,000 | ≤ 800 | ≤ 150 (box body + 4 wheel boxes) |
| Character | ≤ 2,500 | ≤ 900 | none (culled beyond 120 m) |
| Weapon | ≤ 600 | none | none |
| Hero prop | ≤ 800 | ≤ 200 | none |
| Buildings, per 256 m chunk | ≤ 60,000 | ≤ 12,000 | ≤ 2,000 (skyline slabs) |
| Street furniture instance | ≤ 400 | ≤ 80 | none |

LOD switch distances are 0–60 m, 60–150 m and 150 m to fog for dynamic models, and the T0016 values of 150 m and fog for chunks. `render/lod.ts` owns the numbers. Assets only carry the levels.

## 4. Buildings: runtime procedural method

The code lives in `game/src/assets/procedural/buildings/` and builds `BufferGeometry` only. The scene objects are made by `game/world/cityMesher.ts`, as T0016 §4.2 rule 3 requires. The inputs are pure `Building` records from `CityData`. The output per chunk is **one merged geometry per shared material** plus collider data, so a chunk costs a few draw calls whatever its building count.

**Pipeline per building:**

1. **Footprint cleanup.** Make the polygon counter-clockwise, merge edges shorter than 1.5 m, and snap near-right angles to 90°. If it is not convex, split it into rectangles; `cityGen` should emit rectangles, L shapes and U shapes only.
2. **Floor plan.** Floor heights are set per style: residential 3.0 m, office/tower 3.6 m, hotel 3.2 m, and a ground floor of 4.5 m for shops and hotels. Floors are `max(1, round((height − ground) / floorH)) + 1`. The final height is then recomputed, so window rows always line up.
3. **Massing (style grammar).**
   - `downtown_tower`: a podium of 2–3 floors at the full footprint. The tower above is inset 2–4 m, with 0–2 setbacks (another 2–3 m inset every 8–15 floors, chosen by the seed). It has a crown: a flat roof, a stepped roof or a helipad box.
   - `beach_hotel`: a slab with balcony strips facing the sea side (the edge closest to the coastline from `zones`), a ground-floor colonnade, rounded corners (each corner chamfered into 3 segments, which reads as the period's streamline style) and a rooftop sign frame.
   - `beach_shop`: 1–2 floors with an awning box over the shopfront and a neon sign plane.
   - `res_house`: 1–2 floors with a hip roof or a flat roof with parapet, set back from the plot edge.
   - `res_lowrise`: 3–6 floors with external walkway boxes on one side.
   - `ind_warehouse` and `air_hangar`: a single tall volume with a shallow gable or barrel roof (8-segment arc) and roller-door insets.
   - `air_terminal`: a long low box with a glass curtain wall material.
4. **Facades.** Each footprint edge is split into **bays** about 3 m wide (`bays = max(1, round(edgeLen / 3))`). Each floor × bay is one quad with UVs into that style's **facade atlas** (§6). The atlas has cells for wall-only, window, double window, door, shopfront, balcony window and blank. The seed picks a per-building pattern (for example every bay windowed, or alternating), and a per-building tint goes into a vertex colour, so one material covers a whole district with visible variety. Windows are **texture, not geometry**, which is what keeps LOD0 inside budget.
5. **Night lighting.** The atlas has an emissive mask for windows. A per-vertex `aLit` value (0/1, seeded about 35% lit) multiplies it, so windows switch on at dusk through one material uniform driven by `TimeOfDay`, with no per-building work.
6. **Roof.** A flat cap with a 0.6 m parapet. Roof clutter (AC units, water tanks, antennas, stair boxes) is placed by the seed and rendered as `InstancedMesh` per chunk, not merged.
7. **LOD0 details** (only within 150 m): balcony slabs, awnings, colonnade pillars and sign planes, all simple boxes merged into the chunk geometry.
8. **Merge per chunk.** Call `BufferGeometryUtils.mergeGeometries()` (Three.js addon, present in r187) once per material. Keep a `buildingId → [indexStart, indexCount]` table so debug tools can highlight a building.
9. **LOD1.** The same footprint extruded once (walls and roof, no details) with the same atlas UVs, so windows still read from a distance. This is generated in the same pass.
10. **LOD2.** One box per building merged into a "skyline" mesh with a cheap material, used beyond 150 m up to the fog distance.
11. **Colliders (data only, for `cityColliders.ts`).** Use one oriented box per footprint rectangle, `{center, halfExtents, rotationY}`, at full height. Setbacks add one box per tier. Trimesh colliders are not used for buildings because boxes are cheaper in Rapier and good enough for cars and the camera.
12. **Disposal.** The chunk owner keeps references to every geometry it created and disposes them when the chunk unloads. The memory baseline test in T0016 §5 covers this.

**Roads, sidewalks and ground** follow the same pattern: ribbons extruded along `RoadEdge` polylines with lane-marking UVs, junction polygons from node fans, and kerb strips 0.15 m high. Each is merged per chunk per material. T0022 owns the exact algorithm; this design fixes only the material names (§8.3) and the UV scale (1 UV unit = 4 m on asphalt).

**Street furniture** geometry is built once at boot by small functions in `src/assets/procedural/props/` (for example, a palm is a tapered 6-sided trunk with 8 curved frond strips and seeded lean), then drawn with one `InstancedMesh` per prop type per chunk (T0017 rule: batch by chunk, not city-wide).

## 5. Vehicles, character, weapons and props: build-time glTF method

### 5.1 Toolchain (versions checked on npm on 2026-11-26)

| Tool | Version | Use |
|---|---|---|
| Node | 24 LTS (tested on 24.22.3) | Runs the scripts with `node --experimental-strip-types` or `tsx` (T0019's choice) |
| `three` | 0.187.0 | Builds the meshes, plus `GLTFExporter` (`three/addons/exporters/GLTFExporter.js`) |
| `@gltf-transform/core`, `/functions`, `/extensions` | 4.5.1 | Post-processing: `dedup`, `weld`, `prune`, `meshopt` |
| `meshoptimizer` | 1.3.0 | Encoder for `EXT_meshopt_compression` |
| `gltf-validator` | npm package (reports validator 2.0.0-dev.3.10) | Spec validation in the build and in tests |

All of these are **dev dependencies**. At runtime the game needs only `three` (with its bundled `meshopt_decoder.module.js`), which T0016 already lists.

**One known Node gap, handled:** `GLTFExporter` with `binary: true` uses `FileReader`, which Node 24 does not provide (`typeof FileReader === 'undefined'`; I checked). The pipeline installs a 6-line `FileReader` shim built on `Blob.arrayBuffer()` (`tools/assets/lib/nodeShims.ts`, shown in §9). Since no textures go into the `.glb` files, no canvas or image encoding is needed in Node. **Fallback:** if the shim ever breaks after a Three.js upgrade, the generators can write geometry straight into a glTF-Transform `Document`, which is Node-native. This costs more code but has no browser APIs.

### 5.2 Vehicles (`tools/assets/gen/vehicles.ts`)

Each vehicle is a **parameter row**, not a model:

```ts
interface VehicleShape {
  id: `vehicle.${string}`;            // 'vehicle.sedan01'
  length: number; width: number; height: number;   // metres
  wheelbase: number; track: number; wheelRadius: number; wheelWidth: number;
  groundClearance: number;
  profile: Array<[z: number, y: number]>;  // side silhouette, front (+Z) to back, 10–16 points
  cabin: { zFront: number; zBack: number; roofY: number; taper: number };  // glass house
  bumpers: boolean; spoiler?: boolean; roofSign?: 'taxi' | 'siren';
  paint: 'tintable' | string;         // police/taxi use fixed palette ids
}
```

**Method:**
1. **Body.** Extrude the side `profile` across the width with a small bevel (`ExtrudeGeometry`, `bevelSegments: 1`). Then pinch the top edge inward by `taper` so it is not a slab. The result is about 300–900 triangles.
2. **Glass house.** A second extruded profile between `cabin.zFront` and `cabin.zBack`, inset 5 cm, using `mat_glass`.
3. **Wheel arches.** Cut by boolean-free means: the profile polyline gets an arc notch at each axle, so no CSG library is needed.
4. **Wheels.** One cylinder (16 sides at LOD0, 8 at LOD1) plus a rim disc, as **separate nodes** `wheel_FL/FR/RL/RR`. Each wheel's origin is the wheel centre, so the physics transform can drive it directly.
5. **Lights.** Small emissive boxes in their own nodes (`light_head_L/R`, `light_brake_L/R`, plus `light_siren_L/R` for police) so the light system can toggle them or swap the emissive strength.
6. **Sockets.** Empty nodes for gameplay: `socket_seat_driver`, `socket_door_L`, `socket_door_R` (where a character stands to enter), `socket_exhaust` (smoke and backfire), `socket_engine` (fire and smoke at low health) and `socket_camera` (in-car camera target).
7. **LODs.** The same function is called with lower segment counts (and LOD2 as boxes), producing three child groups `lod0/lod1/lod2` under the root. Wheels and sockets sit directly under the root and are shared by all levels. LOD2 hides the wheel meshes.
8. **Paint variation.** The body uses `mat_paint`. At spawn, the runtime picks from an 8-colour 1980s-coast palette and gets one cached material clone per colour, so a full traffic load has at most 8 paint materials.
9. **Physics hand-off.** The generator writes the true wheel centres, radius, chassis half-extents and centre of mass into the manifest `meta` (§7). T0020's `VehicleDef` **reads these instead of re-typing numbers**, so the visual wheels and the raycast wheels cannot drift apart.

### 5.3 Character (`tools/assets/gen/character.ts`)

1. **Skeleton.** 19 bones (`root, hips, spine, chest, neck, head`, and `_L/_R` versions of `shoulder, upperarm, forearm, hand, thigh, shin, foot`). The mannequin is 1.80 m tall, facing +Z.
2. **Mesh.** Each body part is a low-poly capsule or box (6–8 sides), rigidly skinned to one bone (weight 1.0). Joint rings at the elbows, knees and hips are blended 50/50 to their two bones so bends do not tear. One `SkinnedMesh`, ≤ 2,500 triangles. Materials `mat_skin`, `mat_cloth_top`, `mat_cloth_bottom`, `mat_shoe`, all tintable for crowd variety.
3. **Clips.** Each clip is written as a keyframe table in code: about 4–8 keys per bone of quaternions per clip, sampled from simple periodic functions (for example, a walk cycle is thigh swing = A·sin(2πt/T), with knee bend phase-shifted). Each table is turned into `THREE.AnimationClip` objects and passed to the exporter's `animations` option. Root motion is **not** baked; the controller moves the capsule (T0021).
4. **Sockets.** `socket_hand_R` (weapon grip), `socket_head` (hats/hair blocks), plus a `socket_seat` offset so the sitting pose lines up with `socket_seat_driver`.
5. **Runtime cloning** uses `SkeletonUtils.clone()` (Three.js addon, present in r187) so each ped gets its own skeleton.

### 5.4 Weapons and hero props (`gen/weapons.ts`, `gen/props.ts`)

Boxes, cylinders and simple extrusions only. Weapons carry `socket_grip` (the origin) and `socket_muzzle`. Props carry a `collider` record in the manifest (`box` half-extents or `cylinder` radius and height) and a `mass` for dynamic ones (cone 3 kg, barrier 20 kg, crate 25 kg, dumpster static). Pickups use `mat_pickup_*` emissive materials and spin at runtime.

### 5.5 Build steps (`npm run assets` → `tools/assets/build.ts`)

```
for each definition (vehicles, character, weapons, props):
  1. generate   Object3D tree from (params, seed)              [gen/*.ts]
  2. lint       names, origin, axes, sockets, LOD groups,
                triangle budget per LOD                        [lib/checks.ts]   → fail build on error
  3. export     GLTFExporter.parseAsync(scene, {binary:true,
                animations})                                   [lib/exportGlb.ts]
  4. optimise   glTF-Transform: dedup → weld → prune → meshopt [lib/optimize.ts]
  5. validate   gltf-validator: numErrors must be 0            [lib/validate.ts]
  6. write      public/assets/<category>/<name##>.glb
  7. record     bytes, sha256, triangles per LOD, bounds,
                meta, provenance                               → manifest entry
write public/assets/manifest.json (keys sorted, 2-space JSON, stable)
```

- `npm run assets` regenerates everything. Run time for the full set has not been measured yet.
- `npm run assets:check` regenerates to a temp directory and fails if any hash differs from the committed manifest. A Vitest test (`tests/unit/assets.test.ts`) calls the same check, so the existing `npm test` covers it. **No workflow change is needed**, which matters because agents cannot edit `.github/workflows/`.
- **The generated `.glb` files and `manifest.json` are committed.** They are small (about 5 KB per car measured; the full set should be well under 1 MB, an estimate to confirm), and committing them means `npm run dev` and the static deploy work without running generators. It also means a reviewer can see in the manifest diff exactly which assets changed. The determinism check stops hand edits or stale files.

## 6. Textures

### 6.1 v1: procedural canvas textures at runtime (`src/assets/procTextures.ts`)

They are generated once at boot on an `OffscreenCanvas` (or a `<canvas>` as fallback) with seeded value noise plus drawing calls, then wrapped in `THREE.CanvasTexture` with mipmaps and repeat wrapping:

| Texture | Size | Content |
|---|---|---|
| `tex_asphalt_basecolor` | 1024² | Grey noise with sparse aggregate speckles and darker patch stains |
| `tex_asphalt_markings` | 512 × 64 strip | White and yellow lane lines, dashes, stop bar, sampled by road UVs |
| `tex_sidewalk_basecolor` | 512² | Concrete slabs with joint lines |
| `tex_sand_basecolor`, `tex_grass_basecolor` | 512² | Two-octave noise |
| `tex_facade_<style>_basecolor` | 1024² atlas, 4 × 4 cells | Wall, window and door cells for that style, period pastel palettes |
| `tex_facade_<style>_emissive` | 1024² (same layout) | Window glow mask for night |
| `tex_sign_<n>_basecolor` | 512 × 128 | Neon sign faces with **invented** business names from a word list in code |

Normal maps are generated from the same height noise (Sobel filter) for asphalt, sidewalk and facades at the Medium preset and up. Boot cost has to be measured in T0022. If it is above about 300 ms, move to §6.3.

### 6.2 Why not ship image files in v1

Procedural textures add 0 bytes to the download (T0016 size target < 30 MB), need no image codec in Node, and keep every texture provably original.

### 6.3 Later option: KTX2/Basis bake

If GPU memory or boot time is too high, a `tools/assets/gen/textures.ts` step renders the same canvas code in Node or a headless browser to PNG, then runs `gltf-transform etc1s` (colour) or `uastc` (normal maps). **I checked that the glTF-Transform 4.5.1 CLI calls the external `ktx` command from KTX-Software and requires version 4.4.0 or newer.** That is a native binary on the build machine, which is why it is not in v1. If adopted, the runtime adds `KTX2Loader` (with `detectSupport(renderer)`) and the Basis transcoder from `three/examples/jsm/libs/basis/`, both present in r187.

### 6.4 Draco

Draco is not used. Meshopt also compresses animation, decodes faster, and ships as a small decoder inside Three.js. One codec keeps the loader simple.

### 7.2 Manifest schema (`manifest.json`)

This extends T0016's `id → {url, type, bytes, lodLevels}` without breaking it:

```ts
interface AssetManifest {
  schema: 1;
  generator: { three: string; gltfTransform: string; meshoptimizer: string };  // pinned versions
  assets: Record<AssetId, AssetEntry>;   // keys sorted
}
type AssetId = `${'vehicle'|'character'|'weapon'|'prop'|'texture'}.${string}`;
interface AssetEntry {
  type: 'gltf' | 'ktx2';
  url: string;                 // 'assets/vehicle/sedan01.glb'
  bytes: number;
  sha256: string;              // loader appends ?v=<first 8 hex> for cache busting
  lodLevels: number;           // 1–3
  triangles: number[];         // per LOD, e.g. [2410, 760, 132]
  bounds: { min: [number, number, number]; max: [number, number, number] };
  meta?: VehicleMeta | CharacterMeta | WeaponMeta | PropMeta;
  provenance: { generator: string; seed: number; paramsHash: string; license: 'original' };
}
interface VehicleMeta {
  kind: 'vehicle';
  wheels: Record<'FL'|'FR'|'RL'|'RR', [number, number, number]>;   // wheel centres, metres
  wheelRadius: number; wheelWidth: number;
  chassisHalfExtents: [number, number, number]; centerOfMass: [number, number, number];
  sockets: string[]; lights: string[];
}
interface CharacterMeta { kind: 'character'; height: number; bones: string[]; clips: Record<string, number> /* seconds */; sockets: string[] }
interface WeaponMeta    { kind: 'weapon'; sockets: string[] }
interface PropMeta      { kind: 'prop'; collider: { shape: 'box'; halfExtents: [number,number,number] } | { shape: 'cylinder'; radius: number; halfHeight: number }; mass: number /* 0 = static */ }
```

### 7.3 Runtime loader (`src/assets/loader.ts`) contract

- One `GLTFLoader` with `setMeshoptDecoder(MeshoptDecoder)` from `three/addons/libs/meshopt_decoder.module.js` (both confirmed present in three 0.187.0). `setKTX2Loader` is only needed if §6.3 lands.
- `preload(ids, onProgress)` for the loading screen, using manifest `bytes` as the progress weight.
- A cache keyed by id, with **reference counting**: `acquire(id) → handle`, `release(handle)`. When the count reaches zero, geometries are disposed (chunk unload, T0016 §5 memory test).
- `instantiate(id)` returns a clone. Geometry is shared; skinned assets go through `SkeletonUtils.clone`. Named materials are swapped for `MaterialLibrary` instances (§3 rule 4).
- glTF `extras` come through as `userData`. The spike showed that `GLTFExporter` writes `Object3D.userData` to node `extras` and that it survives meshopt optimisation, so the root node also carries `{assetId, generator, seed}` for debugging.

### 7.4 Provenance

`game/ASSETS.md` states that every asset is generated by code in this repository, lists the generators, and says that **no external meshes, textures, fonts or sounds are used**. Any future external file must be CC0 or similarly licensed, listed there with its source URL and licence, and given `license` other than `original` in the manifest. Reviewers fail a PR that adds a binary asset not produced by `npm run assets`. This covers T0017's request that T0018 track asset provenance, and T0016's §0 content rule.

## 8. Naming conventions

### 8.1 Ids and files
- **Asset id:** `^(vehicle|character|weapon|prop|texture)\.[a-z][a-z0-9_]*[0-9]{2}$`, for example `vehicle.sports01` or `prop.pickup_cash01`. The two-digit suffix allows variants (`vehicle.sedan02`).
- **File:** `public/assets/<category>/<name##>.<glb|ktx2>`, derived from the id and never typed by hand.
- **Runtime procedural keys** (not in the manifest): building styles `<district>_<style>` as in §2.1, building instance `b_<chunkX>_<chunkZ>_<index>`, chunk `c_<x>_<z>`, prop types as lowercase snake names (`traffic_light`).

### 8.2 Nodes inside `.glb` files
| Pattern | Meaning | Example |
|---|---|---|
| root = asset id | One root node per file | `vehicle.sedan01` |
| `lod0`, `lod1`, `lod2` | LOD groups under the root | |
| plain lowercase | Mesh parts | `body`, `glass`, `bumper_F` |
| `wheel_FL/FR/RL/RR` | Wheels (T0016), origin at the wheel centre | |
| `light_<kind>_<L/R>` | Light meshes | `light_head_L`, `light_brake_R`, `light_siren_L` |
| `socket_<name>` | Empty attachment points | `socket_seat_driver`, `socket_hand_R`, `socket_muzzle` |
| `_L/_R/_F/_B` suffix | Left/right/front/back from the model's own view (front = +Z, left = +X when facing +Z) | |

### 8.3 Materials (fixed list, `mat_` prefix)
Vehicles: `mat_paint`, `mat_glass`, `mat_tire`, `mat_rim`, `mat_chrome`, `mat_plastic_black`, `mat_light_head`, `mat_light_brake`, `mat_light_siren_red`, `mat_light_siren_blue`, `mat_sign_taxi`.
Character: `mat_skin`, `mat_cloth_top`, `mat_cloth_bottom`, `mat_shoe`, `mat_hair`.
Weapons and props: `mat_metal_dark`, `mat_wood`, `mat_plastic_orange`, `mat_concrete`, `mat_pickup_health`, `mat_pickup_armor`, `mat_pickup_cash`, `mat_marker`.
City (runtime): `mat_asphalt`, `mat_sidewalk`, `mat_kerb`, `mat_sand`, `mat_grass`, `mat_water`, `mat_facade_<style>`, `mat_roof`, `mat_skyline`, `mat_palm_trunk`, `mat_palm_leaf`, `mat_metal_pole`, `mat_neon_<colour>`.
Adding a material means adding it to `MaterialLibrary` and to this list in the same PR.

### 8.4 Bones and clips
Bones are lowercase with `_L/_R` (§5.3). Clips are lowercase snake case with an optional side: `idle`, `walk`, `run`, `jump`, `fall`, `enter_car_L`, `exit_car_L`, `aim_pistol`, `death`.

### 8.5 Textures
`tex_<subject>_<map>` with map ∈ {`basecolor`, `normal`, `orm`, `emissive`, `markings`}, for example `tex_facade_beach_hotel_emissive`.

`lib/checks.ts` enforces 8.1–8.5 with regular expressions, and the build fails on any violation.

## 9. What I tested (spike), with the code

On the CI runner (Node v24.22.3) I installed `three@0.187.0`, `@gltf-transform/core|functions|extensions@4.5.1`, `meshoptimizer@1.3.0` and `gltf-validator` in a scratch folder (`/tmp/spike`, not in the repo), and ran:

1. **Generate and export.** A box body, a glass cabin and 4 cylinder wheels named `wheel_FL/FR/RL/RR`, with materials `mat_paint`, `mat_glass` and `mat_tire`, and root `userData` `{assetId, generator, seed}`. Exported with `GLTFExporter.parseAsync(scene, {binary: true})` after installing this shim:
   ```js
   globalThis.FileReader = class {
     readAsArrayBuffer(b) { b.arrayBuffer().then(r => { this.result = r; this.onloadend?.(); }); }
     readAsDataURL(b) { b.arrayBuffer().then(r => { this.result = `data:${b.type || 'application/octet-stream'};base64,` + Buffer.from(r).toString('base64'); this.onloadend?.(); }); }
   };
   ```
   Result: a 22,632-byte `.glb`.
2. **Optimise.** `NodeIO` with `ALL_EXTENSIONS` and the meshopt encoder/decoder registered, then `dedup(), weld(), prune(), meshopt({encoder: MeshoptEncoder, level: 'medium'})`. Result: **5,236 bytes**, using extensions `EXT_meshopt_compression` and `KHR_mesh_quantization`. Node names, material names and root `extras` all survived.
3. **Validate.** `gltf-validator` `validateBytes`: **0 errors, 0 warnings** for both files. There were info-level messages only: `UNUSED_OBJECT` and, for the compressed file, `UNSUPPORTED_EXTENSION` (the validator does not decode meshopt).
4. **Determinism.** Ran steps 1–2 a second time; the SHA-256 of both files was identical.

I also checked that three 0.187.0 ships `GLTFLoader.setMeshoptDecoder`, `setKTX2Loader`, `libs/meshopt_decoder.module.js`, `libs/basis/`, `KTX2Loader.detectSupport`, `BufferGeometryUtils` and `SkeletonUtils`. I also confirmed that glTF-Transform 4.5.1's KTX2 commands need KTX-Software ≥ 4.4.0.

**Not tested here:** skinned mesh and animation export, the full set of generators, runtime loading in a browser, procedural texture boot time, and building-mesher performance. These belong to the implementation tasks, and the checks in §5.5 and §7 are designed to catch problems there.
