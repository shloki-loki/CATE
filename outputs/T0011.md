# T0011: Modern dashboard design research for CATE (home, models page, top-right theme control)

**Short version:** CATE should look **calm, neutral and dense**, in the style of Linear and Vercel. That means near-neutral grey surfaces with a slight tint, one accent colour (keep CATE's teal), Inter type with tabular numbers, separation by borders and surface shade instead of heavy shadows, and smaller corner radii. The changes with the most impact:

1. **A shared top bar on every page.** Page title on the left. On the right: usage ring, **theme (brightness) button** and sign-out. The sidebar footer and the "show archived" button go away.
2. **Models page rebuilt around "Add a model or API".** A visible 3-step guide and a primary button at the top. Short connection cards, with model and role settings folded away until needed. An optional "team map" node diagram (supervisor → connections → models).
3. **Home page in "composer first" style** like the big chat apps, with a team-status strip and recent projects under it. This follows NN/g's empty-state guidance: show system status and give direct routes into key tasks.
4. **Fix contrast.** I measured today's colours and found real WCAG failures (table below). New tokens that pass are included.
5. **Lists continue in the composer.** Shift+Enter after `1. ` or `- ` adds the next number or bullet. I wrote a small helper and tested it in Node (results below).

All CSS below uses CATE's **existing class and variable names** (`web/app/globals.css`), so it can go in piece by piece.

## 2. Patterns that make dashboards look "professional"

1. **Neutral first, one accent.** Grey surfaces with a tiny hue tint. The accent appears only on the primary action, focus rings, selected state and progress. Linear deliberately cut back blue chrome. CATE's teal can stay, but use it less: today it is on the avatar, banners, chips, plan border and meters all at once.
2. **Elevation by lightness, not shadow (dark mode).** App background < sidebar < card < popover. Hairline borders (Radix steps 6–7) separate areas. Keep shadows only for floating layers: popovers, menus and dialogs.
3. **Role-based tokens.** Name colours by job (bg, surface, hover, border, border-strong, text, text-muted). Geist and Radix both do this, and CATE already half does. Adding the missing `hover`, `selected` and `line-strong` roles fixes most "looks a bit off" states.
4. **Density with hierarchy.** 13–14px UI text, 4px spacing grid, 32–36px control height, section labels in small caps or 12px muted. Headings weight 600 with slightly tighter letter-spacing.
5. **Smaller, consistent radii.** 6px for small controls, 8px for buttons and inputs, 12px for cards and popovers. CATE uses 14–18px cards plus pill buttons, which reads as "consumer app" rather than "pro tool".
6. **Rectangular buttons with clear levels.** Primary (solid accent), secondary (surface + border), ghost (no border), danger (red text). Use pills only for status badges.
7. **Progressive disclosure.** Show status and the one key number up front. Put configuration behind "Configure" or `<details>`. This is how Open WebUI and LobeChat keep provider pages readable.
8. **Status at a glance.** Coloured dot + word ("Connected", "Paused", "Not connected"), never colour alone.
9. **Tabular numbers** in meters, percentages, token counts and tables.
10. **Header holds global controls.** Theme, account and global status sit at the top right. This is the shadcn/Vercel-style layout the user asked for.

- One `.topbar` for every page, replacing `.chat-head` and the `page-head` + `MenuButton` combination. The left side holds the menu button on mobile and the page or project title. The right side holds the **usage ring** (moved from the composer, which also clears space there), the **theme button** and sign-out.
- **Remove `.side-foot`.** It only held archive, theme and sign-out. Removing the archive toggle and `archived` state matches "show archived projects is not required right now". The archive action on a single project can stay.

### Behaviour (from Chrome's guidance and Lea Verou)
- Icon button with **two states**: it shows what you will switch to (sun when dark, moon when light), with `aria-label="Switch to light theme"`.
- First visit follows the OS (`prefers-color-scheme`). Today CATE always starts dark and *always* stores the choice, so users can never get back to "follow system".
- On click: target = the opposite of what is on screen. If the target equals the OS setting, **remove** `cate-theme`; otherwise store it. Then CATE follows the OS again.
- Keep the existing pre-paint inline script in `app/layout.js` so the page does not flash. Listen for `storage` so other open tabs update too.
- Optional: a small popover under the button offering Light · Dark · System (with "System (currently dark)"). Chrome's guidance puts three-way choices in a settings surface, so keep the one-click button as the main control.
- *Interpretation note:* I read "brightness operator bar" as the light/dark theme control. If the owner meant a brightness *slider*, the same top-right slot works for a slider popover. A CSS `filter: brightness()` on `.main` is not recommended because it dims images and text unevenly and hurts contrast.

### Code sketch
```js
// components/ThemeButton.js
'use client';
import { useEffect, useState } from 'react';
import { Moon, Sun } from '@/components/Icons';

const KEY = 'cate-theme';
const systemDark = () => window.matchMedia('(prefers-color-scheme: dark)').matches;
const apply = (t) => { document.documentElement.dataset.theme = t; };

export default function ThemeButton() {
  const [theme, setTheme] = useState('dark');
  useEffect(() => {
    setTheme(document.documentElement.dataset.theme || 'dark');
    const mq = window.matchMedia('(prefers-color-scheme: dark)');
    const sync = () => {
      let saved = null; try { saved = localStorage.getItem(KEY); } catch {}
      const t = saved || (mq.matches ? 'dark' : 'light'); apply(t); setTheme(t);
    };
    mq.addEventListener('change', sync); window.addEventListener('storage', sync);
    return () => { mq.removeEventListener('change', sync); window.removeEventListener('storage', sync); };
  }, []);
  const flip = () => {
    const next = theme === 'dark' ? 'light' : 'dark';
    try {
      if ((next === 'dark') === systemDark()) localStorage.removeItem(KEY); // back to "follow system"
      else localStorage.setItem(KEY, next);
    } catch {}
    apply(next); setTheme(next);
  };
  const label = theme === 'dark' ? 'Switch to light theme' : 'Switch to dark theme';
  return <button className="icon-btn" onClick={flip} aria-label={label} title={label}>{theme === 'dark' ? <Sun /> : <Moon />}</button>;
}
```
Pre-paint script in `app/layout.js`. It replaces the current one, which only handles `light`:

(If the owner wants CATE to stay **dark by default** whatever the OS says, keep `'dark'` as the fallback instead of `matchMedia`. That is a product choice.)

## 9. Composer: bullets and numbering continue on Shift+Enter

Today `components/Chat.js` (textarea `onKeyDown`, around line 403) sends on Enter and lets Shift+Enter insert a plain newline, so lists never continue. The behaviour below matches GitLab, GitHub and markdown editors: Shift+Enter on `1. text` gives `2. `; on `- text` gives `- `; Shift+Enter on an **empty** item removes the marker and leaves the list; `- - -` and `***` are treated as rules, not lists.

```js
// lib/listContinue.js: tested (see below)
export function continueList(value, caret) {
  const start = value.lastIndexOf('\n', caret - 1) + 1;
  const line = value.slice(start, caret);
  if (/^\s*([-*_])(\s*\1){2,}\s*$/.test(line)) return null;          // "- - -" / "***" is a rule, not a list
  const m = line.match(/^(\s*)(?:([-*+•])|(\d+)([.)]))\s+(\[[ xX]\]\s+)?/);
  if (!m) return null;
  const [marker, indent, bullet, num, punct, box] = m;
  if (line.trim() === marker.trim()) {                                  // empty item: leave the list
    return { value: value.slice(0, start) + value.slice(caret), caret: start };
  }
  const next = bullet ? `${indent}${bullet} ` : `${indent}${Number(num) + 1}${punct} `;
  const insert = `\n${next}${box ? '[ ] ' : ''}`;
  return { value: value.slice(0, caret) + insert + value.slice(caret), caret: caret + insert.length };
}
```
Wiring it into the existing textarea (controlled value; put the caret back after React re-renders):
```js
onKeyDown={(e) => {
  if (e.key !== 'Enter' || e.nativeEvent.isComposing) return;
  if (!e.shiftKey) { e.preventDefault(); submit(); return; }
  const el = e.currentTarget;
  if (el.selectionStart !== el.selectionEnd) return;              // let the browser replace a selection
  const r = continueList(el.value, el.selectionStart);
  if (!r) return;                                                  // normal Shift+Enter newline
  e.preventDefault();
  updateText(r.value);
  requestAnimationFrame(() => { el.selectionStart = el.selectionEnd = r.caret; fitHeight(el); });
}}
```
Test run (Node 20+, my own test file):
```
"1. one"      -> "1. one\n2. "
"a\n9) nine"  -> "a\n9) nine\n10) "
"- item"      -> "- item\n- "
"  * nested"  -> "  * nested\n  * "
"- [x] done"  -> "- [x] done\n- [ ] "
"1. one\n2. " -> "1. one\n"        (empty item leaves the list)
"- - -"       -> null              (rule, not list)
"plain text"  -> null
"• bullet"    -> "• bullet\n• "
```
The `isComposing` check stops Enter from sending while someone is typing with an IME (Japanese, Chinese, Hindi transliteration). Also update the composer note to "Enter to send · Shift+Enter new line (lists continue)". I only unit-tested the pure function; the React wiring above has not been run in the app.
