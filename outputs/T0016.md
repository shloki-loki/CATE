# T0016: Architecture for a browser open-world crime/driving game

Author: claude-2. Status: architecture plan. No code is in this task; code starts in T0019.

## 0. Scope, constraints and one content rule

**The user asked for:** a "GTA Vice City" game that runs in the browser, built from scratch, as realistic as possible, and good enough to play through once.

**Content rule, which every later task must follow:** we build an **original game in the same genre**. That means a third-person open-world city where you walk, drive, steal cars, get a wanted level and play missions, set in a sunny 1980s-style coastal city. We do **not** copy Rockstar's names, map layout, characters, story, music, logos, vehicle designs or UI art. The working title is **"Neon Coast"** and the city is fictional. All assets are generated by us (procedural or hand-written code), which also fits the user's "make it from scratch". Reviewers should fail any task that imports ripped assets or trademarked names.

**Target and constraints**

| Item | Decision |
|---|---|
| Platform | Desktop browser: current Chrome, Edge and Firefox. Safari is best-effort. No install. Runs with `npm run dev` or as a static build. |
| Input | Keyboard and mouse (pointer lock) first. Gamepad (Gamepad API) second. No touch in v1. |
| Performance target | 60 fps at 1080p on a mid-range laptop GPU, with a playable 30 fps floor on integrated graphics through a "Low" preset. These are targets to measure against, not promises. |
| Size target | First playable load under about 30 MB, since most content is procedural. |
| Persistence | Single player. Saves go to `localStorage`/IndexedDB. No server. |
| "Realistic" means | PBR materials, shadows, a day/night cycle with sky and fog, believable car handling (raycast suspension and tyre friction), traffic and pedestrians that follow roads, collision damage and sound. It does **not** mean photoreal scanned assets, which are impossible from scratch in this effort. |

## 1. Tech stack, with the reasons

| Layer | Choice | Why this choice | Alternatives we rejected, and why |
|---|---|---|---|
| Language | **TypeScript** (`strict: true`) | Several different AI models will write modules separately. Typed interfaces at module boundaries catch integration mistakes at build time instead of at runtime. | Plain JS: too easy for agents to break each other's contracts. |
| Build/dev server | **Vite** | Starts with no config, has fast HMR, supports WASM and workers (`?worker`) natively, and outputs a static `dist/` that can be opened locally or hosted on GitHub Pages. | Webpack: slower and more config. Parcel: less common in three.js examples. |
| Rendering | **Three.js** (`WebGLRenderer` by default) | Largest WebGL ecosystem and documentation, which makes agents less likely to hallucinate APIs. It has the pieces we need: glTF/KTX2/Draco loaders, `InstancedMesh`/`BatchedMesh` for thousands of buildings and props, `LOD`, shadow maps, a Sky shader, and post-processing. MIT licence. | Babylon.js and PlayCanvas are strong all-in-one engines. **T0017 benchmarks them formally.** We default to Three.js so T0019 is not blocked, and this document limits engine-specific code to `src/render/` so a switch would stay contained. |
| Renderer backend | WebGL2 now. `WebGPURenderer` (`three/webgpu`) is optional later behind a flag. | WebGL2 runs everywhere. Three.js is actively improving WebGPU, but community reports in 2026 still show CPU overhead regressions in scenes with many meshes, which describes a city. Revisit after v1. | — |
| Physics | **Rapier** (`@dimforge/rapier3d-compat`) | Rust compiled to WASM: fast and deterministic. It ships official TypeScript typings. It has the two controllers this genre needs built in: **`DynamicRayCastVehicleController`** (raycast wheels with suspension, engine force, brake, steering and friction slip) and **`KinematicCharacterController`** (walking with slopes and steps). Normal JS objects, so no manual `Ammo.destroy()` memory management. The `-compat` build embeds the WASM, so no bundler WASM setup is needed. Apache-2.0. | **Ammo.js** (Bullet port, suggested in the brief): `btRaycastVehicle` is proven, but the API is C++-shaped, objects must be freed by hand (leaks are common), typings are unofficial, and builds are hard to obtain and update. Kept as **fallback only**: the `PhysicsAPI` boundary in §4 allows a swap. **cannon-es**: pure JS and easy, but slower with hundreds of bodies (traffic and props). |
| Audio | **Web Audio API** directly, wrapped in our own `AudioAPI`. Three.js `AudioListener`/`PositionalAudio` handle 3D positioning. | "From scratch" means engine, siren, horn, gunshot and ambience sounds are **synthesised** (oscillators, noise and filters) or generated offline by scripts. Web Audio does this natively. | Howler.js: built for file playback, not synthesis. |
| UI / HUD | **Plain DOM + CSS overlay** for HUD and menus. A **2D `<canvas>`** for the minimap and full map, drawn from the road graph. | Text, menus and layout are trivial in DOM. The minimap is a top-down vector draw of data we already have. No framework, so no extra bundle size or render loop. | React/Vue: overkill for about 10 widgets and adds a second update loop. In-scene 3D UI: harder to make sharp and readable. |
| ECS / game objects | A small **hand-written entity/component/system layer** in `src/core/ecs/` (about 200 lines): numeric entity ids, typed component stores and ordered systems. | Gives every agent the same pattern ("write a system that reads components X and Y"), keeps update order explicit, and avoids learning a library. | bitECS: fast, but its struct-of-arrays style is awkward for agents to write correctly. Deep class inheritance: tangles vehicles, peds and police together. |
| Maths | `three` maths types (`Vector3`, `Quaternion`, `Matrix4`) used everywhere | One maths library avoids conversions. Only render code touches the scene graph (§4 rules). | gl-matrix: a second maths library to convert between. |
| Assets | **glTF 2.0 binary (`.glb`)**, meshopt or Draco compression, **KTX2** (Basis) textures | The web standard. Three.js loads it natively. Exportable from code with `GLTFExporter` in Node scripts. **T0018 owns the details.** | FBX/OBJ: no PBR or compression, and slow to parse. |
| Tests | **Vitest** for pure logic (road graph, AI, wanted level, missions, physics adapter run headless with Rapier in Node). **Playwright** for one smoke test: the page boots, a canvas renders, no console errors. | "No errors" was an explicit user demand, so CI must prove the game boots. | — |
| Lint/format | ESLint (with `import/no-restricted-paths` to enforce §4 boundaries) and Prettier | Module boundaries are enforced by tooling, not by trust. | — |

**Dependency list for T0019:** `three`, `@dimforge/rapier3d-compat`. Dev dependencies: `typescript`, `vite`, `vitest`, `@playwright/test`, `eslint`, `prettier`, `@types/three`. Nothing else at runtime without a written reason in the PR.

**Where the code lives:** CATE agents work through PRs on this repo (AGENTS.md rule 7). The game should go in a top-level **`game/`** directory with its own `package.json`, merged through PRs from `cate/<task>-...` branches. A long-lived `browser-gta` branch, as T0019 suggests, would never be reviewed or merged under rule 7, so T0019 should use `game/` instead.

Dependencies only point **downward**. Core does not import gameplay. Gameplay systems talk to each other through **components** (shared data) and **events**, never by importing each other's internals.

## 3. Components

Each component lists its responsibility, the public API it exposes, and the task that owns it.

### 3.1 Engine core (`src/core/`), owned by T0019
- **GameLoop**: a fixed-timestep simulation at 60 Hz (`dt = 1/60`, at most 5 substeps per frame to avoid a spiral of death) and render once per `requestAnimationFrame` with interpolation `alpha` between the last two physics states. It pauses when the tab is hidden.
- **ECS World**: `createEntity()`, `destroyEntity(id)`, `add(id, Component, data)`, `get(id, Component)`, `query(A, B, …)`, and `addSystem(system, phase)`. The phases are `input → preSim → physics → postSim → ai → gameplay → camera → render → ui`.
- **EventBus**: typed pub/sub `on<E>(type, fn)` / `emit<E>(type, payload)`. Events are queued and flushed once per sim tick, so they never fire re-entrantly mid-physics.
- **Services**: one `Services` object passed to every system (`physics`, `render`, `audio`, `input`, `assets`, `events`, `settings`, `time`). No global singletons, which keeps tests easy to mock.
- **Settings**: quality presets (Low/Medium/High), key bindings and volume, persisted to `localStorage`.
- **TimeOfDay**: a game clock (1 real minute = 1 game hour by default) that drives lighting, traffic density and shop/street-light state.

### 3.2 Rendering (`src/render/`), owned by T0019 (base) and T0022 (city)
- `Renderer`: wraps `WebGLRenderer`, handles resize and pixel-ratio cap, tone mapping (ACES), sRGB output, and quality presets.
- `SceneManager`: the root scene plus layers for static world, dynamic entities and debug.
- `Lighting`: a sun `DirectionalLight` with **cascaded shadow maps** (three's CSM addon) or a single shadow camera that follows the player on Low; a hemisphere/ambient light; `Sky` and fog colour driven by TimeOfDay; and emissive street lights and windows at night.
- `MaterialLibrary`: a shared set of PBR materials (asphalt, concrete, glass, car paint, palm, sand, water) so draw calls batch well.
- `Instancing`: helpers that turn repeated props (palms, lamps, windows, parked cars) into `InstancedMesh`/`BatchedMesh`.
- `LOD and culling`: per-chunk LOD (high-detail meshes up to about 150 m, then merged low-poly blocks, then impostors or nothing beyond fog distance) plus frustum culling.
- `Water`: an ocean plane with three's `Water` shader for the coast.
- `PostFX` (High preset only): bloom for neon signs, SMAA, mild colour grading for the 80s look.
- `ViewSync` system (render phase): copies the interpolated physics transform into each entity's `Object3D`.
- `DebugDraw`: physics collider wireframes and road-graph lines, toggled with F3.

### 3.3 Physics (`src/physics/`), owned by T0020 (vehicle) and T0021 (character)
- `RapierPhysics implements PhysicsAPI`: **the only file group that imports Rapier.**
- Rigid bodies and colliders: static trimesh or compound boxes for buildings (built per chunk and removed when a chunk unloads), and dynamic boxes/convex hulls for props and cars.
- **Vehicles**: `DynamicRayCastVehicleController` (created with `world.createVehicleController(chassis)`; T0020 checks the exact call against the installed version). Four wheels, each with suspension stiffness, damping, rest length, friction slip and side stiffness. Engine force goes to the driven wheels and brake force to all.
- **Characters**: `KinematicCharacterController` with a capsule collider, autostep and slope limit, gravity applied by us, and snap-to-ground.
- Queries: `raycast`, `shapeCast`, `overlapSphere`, used by weapons, camera collision, AI sensors and interaction prompts.
- Collision groups: `WORLD_STATIC, VEHICLE, CHARACTER, PROP, PROJECTILE, SENSOR, CAMERA_IGNORE`.
- Contact events go to the EventBus as `collision` with impulse magnitude, which drives damage, sounds and crime detection.
- Option for later: move the Rapier world into a Web Worker. The `PhysicsAPI` is already async-safe in shape (commands in, transforms out), so this would not change callers.

### 3.4 World and city (`src/game/world/`), owned by T0022, with assets from T0018
- `CityGenerator` (pure, seeded): coastline and island masks, then **road network** (arterial grid with distortion, plus local streets subdivided by an L-system or recursive block split, a coastal boulevard and bridges between islands), then city blocks, then lots, then building footprints with height by district.
- Districts: beach strip with hotels, downtown towers, residential, docks/industrial and airport. All names are invented.
- **RoadGraph**: the single source of truth for roads. Nodes are intersections. Edges carry lanes, width, speed limit and direction. It is used by city meshing, traffic AI, pedestrians (sidewalks are offset edges), the minimap and mission GPS routing (A*).
- **ChunkStreamer**: the world is split into 256 m × 256 m chunks. Chunks within radius R are loaded (mesh, colliders and parked cars), and far chunks are unloaded with their resources freed. Generation is seeded, so a chunk regenerates identically.
- `Zones`: named areas used for the HUD "entered zone" banner, police response and ped/car spawn tables.
- Output contract: `generateCity(seed, params) → CityData { roadGraph, blocks, buildings, props, spawnPoints, zones, bounds }`, which is plain JSON-serializable data. Renderers and physics consume it. The generator itself never touches Three.js or Rapier, so it can be unit-tested.

### 3.5 Entities and gameplay (`src/game/*`)
- **Player** (`player/`, T0021): an on-foot state machine (`idle/walk/run/jump/fall/aim/enterVehicle/inVehicle/dead`), health/armour/money, interaction (F to enter or exit the nearest vehicle, which can include carjacking an NPC).
- **Vehicles** (`vehicles/`, T0020): `VehicleDef` data (mass, centre-of-mass offset, engine torque curve, gears, max steer, wheel params and dimensions) for about 6 classes (compact, sports, sedan, van, police, motorbike as a stretch goal). Includes `DriveController` (input or AI produces throttle/brake/steer/handbrake), `VehicleDamage` (health from impulse, smoke at low health, then fire, then explosion) and lights (headlights at night, brake lights).
- **Camera** (`camera/`, T0021 on foot, T0020 in car): a spring-arm follow camera that collides against `WORLD_STATIC` with a shape cast, separate presets for on-foot, in-car (speed-based pull-back and FOV) and aim (over-the-shoulder), plus mouse look with a recenter delay.
- **AI** (`ai/`, a follow-up task): traffic drivers follow lane paths on the RoadGraph with a simple intelligent-driver model for gaps and stop-at-junction rules. Pedestrians walk sidewalk edges, flee from gunfire or collisions, and can be car-jacked or hit. Police (cars and officers) pursue using A* on the RoadGraph plus local steering, ram, and leave the vehicle to chase on foot. A **population manager** keeps N cars and M peds alive in a ring around the player (spawn out of view, despawn far away) with density driven by zone and TimeOfDay.
- **Combat** (`combat/`, follow-up): melee, pistol, SMG and shotgun. Hitscan uses `physics.raycast`, with muzzle flash and tracer from render and synthesised sound from audio.
- **Wanted** (`wanted/`, follow-up): listens to crime events (`vehicleStolen`, `pedHit`, `shotsFired`, `copAttacked`), keeps heat at 0 to 5 stars and decays it while out of police sight. It drives the police spawn tier.
- **Missions** (`missions/`, follow-up): missions are **data**, a list of objective steps (`goTo`, `enterVehicle`, `reachBefore(t)`, `destroy`, `lose wanted`, `deliver`) interpreted by a `MissionRunner`. A start marker sits in the world. The runner shows HUD objective text and a GPS route, and gives pay-out on success. The main story is about 5 to 8 short original missions, enough to "play it once".
- **Save** (`save/`): player position, money, mission progress, time of day, and the city seed (the city is regenerated, not stored).

### 3.6 Input (`src/input/`), owned by T0019 (base) and T0021
- Raw keyboard, mouse (pointer lock) and Gamepad API are mapped to **actions** (`moveX, moveY, lookX, lookY, sprint, jump, enterExit, fire, aim, throttle, brake, steer, handbrake, horn, map, pause`).
- Gameplay reads actions only, never key codes. This makes rebinding and gamepad support free.

### 3.7 Audio (`src/audio/`), follow-up task
- `AudioAPI`: `play(soundId, {position?, volume?, loop?}) → handle`, `setParam(handle, name, value)`, `stop(handle)`, and mixer buses (`sfx, ambience, music, ui`).
- `EngineSynth`: an oscillator and noise model driven by RPM and load per vehicle. `Siren`, `Horn`, `Gunshot`, `Impact`, `Ambience` (waves, city hum, wind).
- "Radio": original procedurally generated synthwave loops (a simple step sequencer). We never use real songs.

### 3.8 UI and HUD (`src/ui/`), owned by T0023
- HUD: health/armour bars, money, wanted stars, weapon/ammo, speedometer in a vehicle, zone name banner, mission objective text and a **minimap** (canvas, player-centred and rotating, drawn from RoadGraph and blips).
- Screens: loading screen with progress from Assets, main menu, pause menu with settings and key bindings, full map, mission passed/failed and "wasted/busted" screens (with original wording).
- The UI is **read-only toward gameplay**. It reads state through a `HudModel` snapshot updated once per frame, and sends user intents back only as events (`ui:resume`, `ui:setting`).

### 3.9 Asset pipeline (`tools/` and `src/assets/`), owned by T0018
- **Two paths:**
  1. **Runtime procedural**: buildings, roads, sidewalks, palms and lamps are generated in the browser from `CityData`. This is cheap to ship and endless in variety.
  2. **Build-time generated glTF**: vehicles, the character mannequin with skeleton and code-authored animation clips (walk, run, idle, enter car), and hero props are generated by Node scripts in `game/tools/` using Three.js and `GLTFExporter`, then compressed (meshopt) into `game/public/assets/*.glb`. Textures (asphalt, concrete, facades) are generated as noise-based canvas textures at runtime or baked to KTX2 by scripts.
- `AssetRegistry`: a typed manifest `assets/manifest.json` mapping `id → {url, type, bytes, lodLevels}`. Code asks for `assets.get('vehicle.sports01')`, never a raw path.
- `AssetLoader`: GLTFLoader, KTX2Loader and MeshoptDecoder with a cache, reference counting (for chunk unload) and a progress callback for the loading screen.
- Conventions (T0018 finalizes them): **1 unit = 1 metre, +Y up, model front faces +Z** (the glTF convention), origin at ground centre for buildings and at the axle midpoint on the ground for vehicles. Wheel nodes are named `wheel_FL/FR/RL/RR`. Ids are lowercase dotted `category.name##`.

### 3.10 Debug and tooling
- F3 overlay: fps, draw calls, triangles, physics ms, entity count, current chunk and seed.
- `?seed=123&spawn=x,z&nopeds` URL flags to make bugs reproducible.
- A `window.__game` handle in dev builds only, so tests and agents can inspect state.

### 4.2 Dependency rules (enforced by ESLint `import/no-restricted-paths`)
1. `core/` imports nothing from the project except its own files. Only `three` maths types are allowed.
2. `@dimforge/rapier3d-compat` is imported **only** in `physics/rapier/`. Everyone else uses `PhysicsAPI`.
3. Three.js scene objects (`Mesh`, `Scene`, materials, loaders) are created **only** in `render/`, `assets/`, `game/world/cityMesher.ts` and `*View.ts` files (one view factory per entity type). Gameplay logic files may import only `three` maths classes.
4. `ui/` never imports `game/` modules. It reads `HudModel` and emits events.
5. `game/<a>/` must not import from `game/<b>/` internals. Cross-feature communication uses `game/components.ts`, `game/events.ts` and queries on the ECS world. Shared helpers go in `game/shared/`.
6. Pure generators (`cityGen`, `roadGraph`, mission parsing, wanted logic, AI decision code) have **no** Three.js scene or Rapier dependency, so they are unit-testable in Node.
7. Each module exposes a single `index.ts`. Importing deep paths from another module is a lint error.

### 4.3 Key interfaces (contracts the later tasks implement)
```ts
// core/services.ts
export interface Services {
  physics: PhysicsAPI; render: RenderAPI; audio: AudioAPI; input: InputAPI;
  assets: AssetAPI; events: EventBus<GameEvents>; settings: Settings; time: TimeOfDay;
}
export interface System {
  name: string; phase: Phase;
  init?(world: World, s: Services): void | Promise<void>;
  update(world: World, s: Services, dt: number): void;
  dispose?(): void;
}

// physics/PhysicsAPI.ts
export type BodyHandle = number & { __brand: 'Body' };
export interface PhysicsAPI {
  init(): Promise<void>;                     // loads WASM
  step(dt: number): void;
  createBody(d: BodyDesc): BodyHandle;       // static|dynamic|kinematic + collider shapes + group
  removeBody(h: BodyHandle): void;
  getTransform(h: BodyHandle, out: Transform): Transform;
  setTransform(h: BodyHandle, t: Transform): void;
  applyImpulse(h: BodyHandle, impulse: Vector3, point?: Vector3): void;
  raycast(from: Vector3, dir: Vector3, maxDist: number, mask?: number): RayHit | null;
  shapeCastSphere(from: Vector3, dir: Vector3, radius: number, maxDist: number, mask?: number): RayHit | null;
  createVehicle(d: VehicleDesc): VehicleHandle;      // wraps DynamicRayCastVehicleController
  setVehicleInput(v: VehicleHandle, i: { throttle: number; brake: number; steer: number; handbrake: boolean }): void;
  getVehicleState(v: VehicleHandle): VehicleState;   // speed, rpm-ish, wheel contacts/transforms
  createCharacter(d: CharacterDesc): CharacterHandle; // wraps KinematicCharacterController
  moveCharacter(c: CharacterHandle, desiredDelta: Vector3, dt: number): { grounded: boolean };
  onContact(fn: (e: ContactEvent) => void): () => void;
}

// render/RenderAPI.ts
export interface RenderAPI {
  init(canvas: HTMLCanvasElement): Promise<void>;
  addToWorld(obj: Object3D, layer: 'static' | 'dynamic' | 'debug'): void;
  remove(obj: Object3D): void;
  camera: PerspectiveCamera;
  setTimeOfDay(hours: number): void;
  setQuality(q: 'low' | 'medium' | 'high'): void;
  render(alpha: number): void;
  stats(): { drawCalls: number; triangles: number };
}

// game/world/cityGen/types.ts  (pure data, JSON-serializable)
export interface CityData {
  seed: number; bounds: Rect;
  roadGraph: { nodes: RoadNode[]; edges: RoadEdge[] };   // edges: lanes, width, speedLimit, oneWay
  blocks: Block[]; buildings: Building[];                // footprint polygon, height, style, district
  props: PropPlacement[]; spawnPoints: SpawnPoint[]; zones: Zone[];
}
```

### 4.4 Shared components (`game/components.ts`), first set
`Transform`, `PrevTransform` (for interpolation), `RigidBody {handle}`, `View {object3D}`, `Vehicle {defId, handle, health, occupants[]}`, `Driver {mode: 'player'|'ai'|'none'}`, `Character {handle, state}`, `Health {hp, armor}`, `PlayerTag`, `PedAI {path, state}`, `TrafficAI {laneRoute, targetSpeed}`, `PoliceAI {target, tier}`, `Weapon {id, ammo, cooldown}`, `Blip {icon, color}`, `MissionTarget {missionId, step}`, `Streamed {chunkId}` (despawned together with its chunk).

### 4.5 Events (`game/events.ts`), first set
`collision {a, b, impulse, point}`, `vehicleEntered {entity, vehicle, stolen}`, `vehicleExited`, `damage {target, amount, source, kind}`, `death {entity, cause}`, `shotsFired {pos, weapon}`, `crime {kind, pos, severity}`, `wantedChanged {stars}`, `zoneEntered {zone}`, `missionStarted|Step|Passed|Failed`, `chunkLoaded|Unloaded {chunkId}`, `ui:pause|resume|setting`.

### 4.6 Frame order (one sim tick, then render)
```
input.poll → (actions) → player/AI DriveController & character intent (preSim)
→ physics.step(1/60) → contact events queued (physics)
→ copy body transforms → Transform; Prev saved (postSim)
→ ai (traffic, peds, police) → gameplay (combat, wanted, missions, damage, streaming)
→ events.flush()
render frame: camera system → viewSync(alpha) → render.render(alpha) → ui.update(HudModel)
```

## 5. Performance budget (targets to measure with the F3 overlay)
| Budget | Target (Medium) |
|---|---|
| Frame time | ≤ 16.6 ms total: sim ≤ 6 ms (physics ≤ 3, AI ≤ 2), render submit ≤ 6 ms |
| Draw calls | ≤ 600, reached with instancing, merged static chunk geometry and a shared material library |
| Visible triangles | ≤ 1.5 M |
| Live dynamic actors | about 40 traffic cars, about 60 peds, ≤ 8 police units within the active ring |
| Loaded chunks | 5 × 5 around the player (Low: 3 × 3) |
| Memory | JS heap under 600 MB. Chunk unload must free GPU geometry and physics bodies, and a test checks the counts return to baseline. |

## 7. Risks and mitigations
| Risk | Mitigation |
|---|---|
| Parallel agents produce code that does not fit together | Typed interfaces in §4.3, a single `components.ts`/`events.ts`, lint-enforced boundaries, and every PR must pass `tsc`, Vitest and the smoke test. |
| Car handling feels bad (the genre's most important feel) | Tunable `VehicleDef` data, a dev panel (lil-gui, dev builds only) for live tuning, and a reviewer drive-test checklist. |
| City too heavy for the browser | Chunk streaming, instancing, LOD, fog distance and the Low preset, measured against §5. |
| Animated humans from scratch are hard | v1 uses a code-generated low-poly mannequin with procedural or code-authored clips. Realism comes from the environment, lighting and vehicles. |
| Rapier vehicle controller docs are thin (the class reference has no usage guide) | T0020 starts from the official class reference and the open-source examples, and writes headless Vitest tests for the controller (car accelerates, stops and turns on flat ground). The `PhysicsAPI` boundary keeps Ammo.js available as a fallback. |
| IP / copying | §0 content rule. Reviewers reject copied names, maps, music or assets. |
| "Perfect, no errors" expectation | Stated honestly: this is a scoped original genre game for one playthrough, not a full commercial-scale replica. Quality is enforced through CI checks and a final integration task. |
