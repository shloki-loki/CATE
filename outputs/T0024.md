## Defects found (each must be fixed before approval)

**D1. `prune()` deletes every socket node.** `prune()` with default options removes empty leaf nodes. T0018 §5.2–5.4 make sockets empty nodes: `socket_seat_driver`, `socket_door_L/R`, `socket_exhaust`, `socket_engine`, `socket_camera`, `socket_hand_R`, `socket_grip`, `socket_muzzle`. In my run, `socket_seat_driver` and `socket_exhaust` were missing after optimisation, and glTF-Transform logged `prune: Removed types... Node (1)`. The validator still reported 0 errors, so the §5.5 gate would not catch this. T0018's own test had no sockets, which is why it missed this.
*Fix:* use `prune({ keepLeaves: true })`. I verified that `socket_exhaust` then survives export → meshopt → `GLTFLoader`. Also add a post-optimisation check in `lib/checks.ts` that every socket and light listed in the manifest `meta` still exists in the written file.

**D2. The root node name `vehicle.sedan01` does not survive loading.** `GLTFLoader` passes node names through `PropertyBinding.sanitizeNodeName`, which strips `.`. As a result, `sanitizeNodeName("vehicle.sedan01")` returns `vehiclesedan01`, and `scene.getObjectByName('vehicle.sedan01')` returns nothing after load. The original name only survives in `userData.name`. §8.2 ("root = asset id") and any code that looks up the root by id would fail without an error.
*Fix:* name the root `vehicle_sedan01` (id with `.` replaced by `_`; I verified it survives), keep the real id in root `extras.assetId` (verified to survive), and have the loader find the root through `userData.assetId`. Add a rule to §8.2: node, bone and clip names must match `[A-Za-z0-9_]` only, because Three.js strips `.`, `:`, `/`, `[`, `]` and spaces.

**D3. Skinned character export gives a validator warning the design does not mention.** With the root group above the `SkinnedMesh` (as §8.2 requires), the validator reports `NODE_SKINNED_MESH_NON_ROOT` (a warning, 0 errors). Loading still worked: the skinned mesh, both bones and the `walk` clip loaded, and `SkeletonUtils.clone` gave a separate skeleton. My test was a 2-bone mesh, not the full 19-bone rig.
*Fix:* say whether warnings are allowed, and either put the `SkinnedMesh` at scene root level or list this warning as accepted in `lib/validate.ts`, so it is not later "fixed" in a way that breaks the hierarchy. §9's "skinned export not tested" can then be updated.

**D4. The manifest schema conflicts with the merged skeleton.** T0018 §7.2 uses `schema: 1`. The merged `game/src/assets/registry.ts` (PR #6) requires `version: 1` and throws `manifest: unsupported version` otherwise. The committed `game/public/assets/manifest.json` uses `version`. The first T0018-style manifest would stop the game at boot.
*Fix:* use `version: 1` in §7.2, or include an explicit registry migration in the T0020 hand-off row. The registry's `ID_PATTERN` does accept T0018's ids (`vehicle.sedan01`, `prop.pickup_cash01`).

## What I verified (Rapier and Three.js), with versions

Environment: Node v24.22.3, `three` 0.187.0, `@gltf-transform/core|functions|extensions` 4.5.1, `meshoptimizer` 1.3.0, `gltf-validator` (reports 2.0.0-dev.3.10), `@dimforge/rapier3d-compat` 0.21.0. I used T0018's `FileReader` shim, which works as described.

- **Export, compression and validation:** the car `.glb` gave 0 errors and 0 warnings both before and after meshopt. Info messages were `UNUSED_OBJECT` and `NODE_EMPTY` before compression, and `UNSUPPORTED_EXTENSION` after it, because the validator does not decode meshopt. Output was deterministic (identical SHA-256 across two runs) for both the car and the skinned test character.
- **Three.js runtime load in Node:** `GLTFLoader().setMeshoptDecoder(MeshoptDecoder)` parsed the compressed files. Materials `mat_paint`, `mat_glass` and `mat_tire` came through unchanged, as did nodes `lod0`, `body`, `glass` and `wheel_FL/FR/RL/RR`. Wheel world positions matched exactly: FL [0.8, 0.33, 1.35], RR [-0.8, 0.33, -1.35]. Root `extras` (`assetId`, `generator`, `seed`) arrived as `userData`. The two failures are D1 and D2.
- **Rapier 0.21.0:** I built the chassis cuboid from the loaded bounds and added 4 wheels at the loaded wheel centres through `world.createVehicleController(chassis).addWheel(pos, (0,-1,0), (-1,0,0), 0.3, 0.33)`. After 4 s on a ground cuboid, all 4 wheels reported `wheelIsInContact = true`. With the axle at (-1,0,0), rear engine force drove the car toward **+Z**, which matches the design's "front = +Z". In my run, `setIndexForwardAxis` (0 or 2) did not change the direction of motion. `ColliderDesc.cylinder(0.35, 0.15)` and `cuboid(0.5,0.5,0.5)` built correctly. A ray straight down onto a Y-rotated building cuboid (half-height 10 m, top at y = 20) hit at 30 m from y = 50, as expected. Summary: the *data* in T0018's manifest is enough for Rapier, but the design does not state or verify this mapping (M1).

**Not verified:** loading in a real browser (I tested Node only), the full 19-bone rig with all 9 clips, LOD switching, KTX2, and generator run time.
