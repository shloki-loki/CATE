# T0017 — WebGL engine research for Neon Coast

Agent: gpt-1. Research date: 2026-11-26.

**Select Three.js with `WebGLRenderer` (WebGL2) for the first playable release.** Keep the TypeScript/Vite, Rapier and rendering boundaries in the approved `data/outputs/T0016.md` architecture. This is a recommendation based on documented capabilities and project fit, not a claim that Three.js is the fastest engine.

The goal is an original, procedurally built coastal-city driving game, playable in a desktop browser. Three.js supplies the rendering pieces without requiring the team to replace the already planned game loop, physics adapter, DOM HUD or entity system. Babylon.js is the strongest alternative if integrated engine tooling becomes more valuable than the existing architecture; PlayCanvas deserves particular consideration if dense dynamic nighttime lighting becomes the dominant requirement.

## Performance assessment and implementation guidance

All three provide credible foundations. Actual frame rate depends on scene content, shaders, resolution, shadows, browser, hardware and simulation work. No comparable application benchmark was run for this task, so there are no measured FPS, memory or bundle-size rankings. T0016 says T0017 will benchmark formally; this report completes the assigned documentation-based evaluation but **does not fulfill that additional benchmark expectation**. The following measurement procedure is a proposed implementation gate, not a completed experiment.

For Three.js, begin with these project-specific engineering choices:

1. Batch repeated buildings, palms and street furniture by chunk, geometry and material. Recompute bounds when transforms change; do not use one enormous city-wide instance batch. Keep interactive entities independently addressable in the simulation. Three.js documents both draw-call savings and bounding-volume maintenance for [InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html).
2. Use metallic/roughness materials and environment lighting for visual coherence. Spend detail on the player car and nearby streets. Start with one shadow-casting sun, limited shadow distance and a small nearby light pool. Use emissive signs/windows for distant nighttime appearance; emissive surfaces alone do not illuminate their surroundings. These are proposed quality/cost choices, not measured optimal settings.
3. Stream city chunks, reduce distant detail, reuse shared materials, release unused GPU resources, and avoid allocating temporary vectors every frame. Budget traffic physics and pedestrian AI separately: changing the renderer cannot fix a simulation bottleneck.
4. Make expensive effects optional. A Low preset should reduce internal resolution, shadow quality/distance, visible world distance and simulation population. Preserve legibility and driving responsiveness before adding reflections or heavy post-processing.
5. Pin the tested engine version and matching addon imports in the lockfile. Check WebGL2 availability and show a useful unsupported-browser message. Current Three.js `WebGLRenderer` requires WebGL2 and has not supported WebGL1 since r163; “WebGL2 runs everywhere” in T0016 is too broad. Keep WebGPU outside the first-release requirement; this report does not verify the earlier architecture's assertion about WebGPU CPU regressions. [WebGLRenderer documentation](https://threejs.org/docs/pages/WebGLRenderer.html).

### Proposed reproducible performance gate

Use a deterministic, representative city scene: repeated opaque buildings and props, moving cars, animated pedestrians, a day route, and a night route with headlights and streetlights. Record object/triangle/material/light counts and all quality settings. Test a production build over HTTP on identified physical hardware; a headless software renderer is not evidence for laptop GPU performance.

For any engine comparison, use identical geometry/textures, camera route, viewport and internal resolution, equivalent shadows/post-effects, the same WebGL2 backend, and either disable simulation in all three or use identical simulation work. Warm up shader compilation, then record three 60-second runs per scene. Report median and p95 frame times, CPU simulation/render submission time, GPU time where supported, draw calls across all passes, compressed transfer bytes, cold-load time, and resource growth across repeated chunk loads/unloads. Document browser, OS, GPU, driver, power mode and exact package versions. Inspect output quality so reduced visual work is not mistaken for a faster engine.

Retain T0016's **targets**, not promises: 60 FPS at 1080p on a defined mid-range laptop (about 16.7 ms/frame), a playable 30 FPS Low preset on defined integrated graphics (about 33.3 ms/frame), and roughly 30 MB or less for first playable transfer. If these fail, profile the actual bottleneck before considering an engine switch. Three.js exposes rendering/resource counters through `renderer.info`; accumulate all passes rather than accidentally reading only the last one. [Renderer monitoring API](https://threejs.org/docs/pages/WebGLRenderer.html).
